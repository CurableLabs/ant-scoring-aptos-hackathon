1. WHAT DOES THE ANT SCORING SYSTEM DO?
========================================

The ANT Scoring system is a decentralized research proposal evaluation platform.
Researchers submit proposals, authorized experts score them on 5 weighted categories
(scientific merit, feasibility, community alignment, resource efficiency, open science).
Proposals scoring ≥80% are approved for funding. All scores are recorded immutably 
on the blockchain for transparency.


2. MAIN DATA STRUCTURES
========================================

*** Score Category Structs ***
Five categories for scoring research proposals:

- ScientificMeritScores (40% weight)
  Fields: novelty, biological_plausibility, prior_evidence

- FeasibilityScores (25% weight)
  Fields: technical_viability, data_quality, clarity_of_protocol

- CommunityAlignmentScores (20% weight)
  Fields: mission_fit, dao_engagement

- ResourceEfficiencyScores (10% weight)
  Fields: cost_effectiveness, agentic_resource_use

- OpenScienceScores (5% weight)
  Fields: data_protocol_sharing, collaborative_potential

Total weights = 100%

*** ProposalScore Struct ***
Combines all 5 categories plus:
- final_score: u8 - Weighted average (0-100)
- is_passing: bool - True if score ≥80%
- is_fulfilled: bool - Has it been funded/approved?
- scorer_count: u64 - How many judges scored it
- timestamp: u64 - When it was scored

*** Proposal Struct ***
The actual research proposal:
- id: u64 - Proposal number
- submitter: address - Who submitted it
- title, description, ipfs_hash: String - Proposal details
- scores: ProposalScore - The score card
- scorers: vector<address> - List of judges who scored it
- is_active: bool - Still open for scoring?
- submission_time: u64 - When submitted

*** ANTScoringState Struct ***
System's global configuration:
- owner: address - System owner/admin
- proposal_counter: u64 - Total proposals submitted (ever)
- authorized_scorers: vector<address> - List of approved judges
- passing_threshold: u8 - Minimum score to pass (default: 80)
- active_proposal_count: u64 - Currently active proposals


3. MOVE CONCEPTS (vs Solidity)
========================================

*** Module Declaration ***
module ant_scoring::clean_ant_scoring { }
- Like 'contract' in Solidity
- ant_scoring::clean_ant_scoring = namespace (Parent::Child)

*** Imports ***
use std::signer;
- Import libraries/modules
- std:: = standard library

*** Struct Abilities ***
struct MyStruct has store, copy, drop, key { }
- store = Can be stored in global storage
- copy = Can be duplicated
- drop = Can be deleted
- key = Can be stored at top-level under account (ONE per account)
Note: Solidity doesn't need this - all structs can be stored/copied/deleted

*** The Signer Type ***
fun my_function(account: &signer)
- &signer = Reference to caller (like msg.sender in Solidity)
- Must be passed as parameter (not global)
- Use signer::address_of() to get actual address

*** move_to - Store Data ***
move_to(account, data)
- Permanently stores data under account's address
- Can only store each type ONCE per address
- Solidity equivalent: mapping[addr] = data

*** borrow_global - Read Data ***
let state = borrow_global<Type>(address);
- Fetches and reads data from blockchain storage
- Read-only access
- Solidity: Direct state variable access

*** borrow_global_mut - Read & Modify ***
let state = borrow_global_mut<Type>(address);
- Fetches data with write permission
- Can modify the data
- Solidity: Direct state variable access

*** & vs borrow_global ⭐ IMPORTANT ***
& (Reference):
- Reference to data ALREADY in scope
- Just points to it, doesn't fetch
- Example: &scientific_merit, &mut proposal.scorers

borrow_global (Fetch + Reference):
- FETCHES from blockchain THEN gives reference
- Goes to blockchain storage to get it
- Example: borrow_global<ANTScoringState>(@ant_scoring)

Key: borrow_global = fetch + reference, & = reference only

*** acquires Keyword ***
public fun my_function() acquires Type1, Type2 { }
- Declares which resources function will access
- Required when using borrow_global
- Solidity: Not needed

*** @ Symbol ***
@ant_scoring
- Means "the address of"
- @ant_scoring = module's address

*** Entry Functions ***
public entry fun my_function()
- public = anyone can call
- entry = callable from outside (wallets, dApps)
- Solidity: similar to 'external'

*** View Functions ***
#[view]
public fun my_function()
- Read-only, no state modifications
- Solidity: 'view' or 'pure'

*** Data Types ***
Move → Solidity:
- u8 → uint8
- u64 → uint64
- address → address
- bool → bool
- vector<T> → T[]

*** New Functions Learned ***
- assert!(condition, ERROR_CODE) - Check or throw error
- vector::contains(list, item) - Check if item in list
- vector::push_back(&mut list, item) - Add to end
- vector::index_of(list, item) - Returns (found, index)
- vector::remove(&mut list, index) - Remove at index
- exists<Type>(address) - Check if resource exists
- Type casting: (value as u64), (value as u8)
- Tuple unpacking: let (a, b) = function()

*** Resource Ownership Model ***
Move:
- Resources OWNED by accounts
- Stored AT account addresses using move_to
- Each account = ONE instance per type
- Like safety deposit boxes

Solidity:
- Data stored IN contract
- Use mappings to associate with addresses
- Like a central database


4. KEY FUNCTIONS (clean_ant_scoring.move)
========================================

*** initialize() - Lines 92-103 ***
Purpose: Set up system for first time
Who: Owner
Does: Creates ANTScoringState with owner, empty scorers, 80% threshold
Key: Can only be called ONCE per address

*** submit_proposal() - Lines 105-144 ***
Purpose: Researcher submits proposal
Who: Anyone
Parameters: submitter, title, description, ipfs_hash
Flow:
  1. Get submitter address
  2. Increment counters
  3. Create empty_scores (all zeros)
  4. Create Proposal
  5. Store at submitter's address via move_to

Key: proposal_owner = submitter_addr (same address!)

*** score_proposal() - Lines 146-209 ⭐ MOST COMPLEX ***
Purpose: Authorized judge scores proposal
Who: Authorized scorers only
Parameters: scorer, proposal_owner, + 5 score category structs

Key Insight: Judge provides ALL individual scores as parameters!

Flow:
  1. Setup: Get addresses, access state
  2. Security Checks:
     - Is scorer authorized?
     - Does proposal exist?
     - Not already scored by this judge?
  3. Validate: All 12 fields ≤ 100
  4. Record: Add judge to scorers list
  5. Calculate: Weighted final score
     - Average each category internally
     - Apply weights: 40%, 25%, 20%, 10%, 5%
     - Formula: (sci*40 + feas*25 + comm*20 + res*10 + open*5) / 100
  6. Save Scores:
     IF first scorer (count=0): Replace empty scores
     ELSE: Average with existing scores
       Formula: (old_score * old_count + new_score) / (old_count + 1)
  7. Update is_passing flag (≥80%)

Minimum Judges: 1 (not enforced - potential improvement!)
Maximum Judges: Unlimited (keeps averaging)

*** fulfill_proposal() - Lines 211-226 ***
Purpose: Mark passing proposal as approved/funded
Who: Anyone (no authorization check!)
Parameters: fulfiller, proposal_owner
Flow:
  1. Check proposal exists
  2. Check is_passing = true
  3. Check not already fulfilled
  4. Set is_fulfilled = true
  5. Set is_active = false

Key: Final approval step, closes proposal

*** add_authorized_scorer() - Lines 229-240 ***
Purpose: Owner adds new judge
Who: Owner ONLY (security check)
Logic: Check not duplicate, add with vector::push_back
Idempotent: Safe to call multiple times

*** remove_authorized_scorer() - Lines 242-254 ***
Purpose: Owner removes judge
Who: Owner ONLY (security check)
Logic: Find with vector::index_of, remove if found
Idempotent: Safe to call multiple times

*** View Functions - Lines 354-372 ***
Read-only queries (no gas cost):

- get_system_info(): Returns owner, counters, threshold
- get_proposal_info(address): Returns proposal details, scores
- is_authorized_scorer(address): Returns bool if authorized

Use: Dashboard displays, authorization checks


5. HELPER FUNCTIONS (Private/Internal)
========================================

*** validate_scores() - Lines 257-285 ***
- Checks all 12 score fields ≤ 100
- Throws E_INVALID_SCORE if any field > 100

*** calculate_final_score() - Lines 287-309 ***
- Averages each category's fields
- Applies weights (40%, 25%, 20%, 10%, 5%)
- Returns single score 0-100

*** average_scores() - Lines 311-352 ***
- Averages new scores with existing
- Formula: (old * count + new) / (count + 1)
- Returns new ProposalScore with all fields averaged


6. KEY SYSTEM DESIGN INSIGHTS
========================================

*** Proposal Lifecycle ***
Submit → Score (Judge 1, 2, 3...) → Passing (≥80%) → Fulfill → Complete
(is_active=true) → (is_passing=true) → (is_fulfilled=true, is_active=false)

*** Scoring Philosophy ***
- Multiple judges for fairness (but min=1 not enforced)
- Weighted categories (scientific merit most important at 40%)
- Running average (all judges count equally)
- 80% passing threshold

*** Access Control ***
- Owner controls: Who can score (add/remove judges)
- Anyone can: Submit proposals, fulfill passing proposals, view data
- Centralized owner control (could use DAO governance)

*** Resource Storage ***
- Proposals stored AT submitter's address
- ANTScoringState stored AT module address
- Different from Solidity's central storage


7. SOLIDITY MIGRATION PLANNING
========================================

*** Key Differences to Handle ***
Move → Solidity:
- Resources at addresses → Mappings (mapping(uint => Proposal))
- move_to → mapping[id] = data
- borrow_global → Direct state access
- acquires → Not needed
- Struct abilities → Not needed

*** Potential Improvements ***
- Add minimum judges requirement (e.g., 3 minimum)
- Add authorization to fulfill_proposal
- Event emissions (Move code doesn't show events)
- Consider upgradeability patterns
- Gas optimization

OCTOBER 26-NOVEMBER 5, 2025 - FUTURE IMPROVEMENTS (Before Mainnet)
================================================================================

1. ERROR HANDLING
   - Current: String-based errors (good for development)
   - Upgrade to: Custom errors for 50% gas savings
   - Example: error NotOwner(); revert NotOwner();
   - Industry Standard: Used by OpenZeppelin, Uniswap V3, all major protocols
   
2. UPGRADEABILITY
   - Current: Non-upgradeable contract
   - Add: Proxy pattern (UUPS or Transparent Proxy)
   - Reason: Bug fixes and feature additions post-deployment
   - Note: Critical for mainnet but adds complexity
   
3. ACCESS CONTROL
   - Current: Basic onlyOwner modifier
   - Consider: OpenZeppelin AccessControl for role-based permissions
   - Allows: Multiple admins, role delegation, granular permissions
   
4. SECURITY AUDITS
   - Get professional security audit before mainnet
   - Check for: Reentrancy, overflow, access control issues
   - Tools: Slither, Mythril for automated analysis
   - Cost: $5k-$50k depending on complexity
   
5. GAS OPTIMIZATIONS
   - Pack state variables (uint8s together to save storage slots)
   - Use unchecked{} for safe math operations
   - Consider using uint256 everywhere (EVM native type)
   - Optimize loops and storage reads
   
6. TESTING
   - Write comprehensive unit tests (Hardhat/Foundry)
   - Integration tests for full workflow
   - Edge case testing (zero values, max values, overflow)
   - Test coverage: Aim for 90%+ coverage
   
7. EVENTS ENHANCEMENT
   - All state changes have events (already implemented!)
   - Consider adding more indexed parameters for filtering
   - Add block.number to critical events for tracking
   
8. NATSPEC DOCUMENTATION
   - Add /// comments for all functions
   - Document parameters with @param
   - Document returns with @return
   - Example: /// @notice Submits a new proposal for scoring
   
9. PROPOSAL VALIDATION
   - Add maximum proposal limits per user (prevent spam)
   - Add time-based restrictions (cooldown periods)
   - Consider minimum title/description lengths
   - Add proposal categories or tags
   
10. EMERGENCY CONTROLS
    - Add pause functionality for emergencies (OpenZeppelin Pausable)
    - Add emergency withdrawal mechanisms
    - Circuit breaker patterns for critical functions
    - Owner transfer with two-step process

Priority: Items 1, 2, 4, 6 are CRITICAL before mainnet
Priority: Items 3, 5, 7, 8, 9, 10 are recommended but optional
